## 3. 后端 API 提示词(逐接口契约)

### 3.1 站点/内容只读接口
```
GET /api/config → 返回站点配置对象 {title, copyright, keywords, description}。
GET /api/games → 返回 {groups:[{id,label,games:[{id,name,color,is_hot}]}]},按分组顺序 急速/北京/蛋蛋/PK/加拿大/韩国 归类。
GET /api/games/{gid} → 返回单个彩种完整信息(含 odds/columns/interval)。404 若不存在。
GET /api/draws?gid=&page=&size= → 分页历史开奖,按 period 倒序。返回 {total,page,size,draws:[{gid,period,kjtime,numbers,sum}]}。
GET /api/activities → {activities:[...]},按 id 升序。
GET /api/activities/{aid} → 单活动(含富文本 body)。404 若不存在。
GET /api/news 、 GET /api/news/{nid} → 公告列表/详情。
GET /api/partners → {partners:[...]},按 sort 倒序。
GET /api/shop → {categories:[...], goods:[...], hot:[前4个 hot=1 的商品]}。
```

### 3.2 首页聚合
```
GET /api/home → 一次性返回首页所需:
{banners(轮播), hotGames(热门游戏卡), activities(前3), news(前5), hotGoods(前4 hot 商品), rankings(牛人榜前10), gameGroups(=/games 的 groups)}。
```

### 3.3 牛人榜 / 盈利统计(生成型)
```
GET /api/rankings?scope=day|week|month → {scope, rankings:[{rank,name,user,get}]},20 条。
  用固定随机种子(day=1/week=2/month=3)确定性生成:昵称池、账号 vip_xxxx、盈利 get 随 rank 递减。
GET /api/profit?days=7 → 盈利统计:{summary:{totalBet,totalWin,profit,winRate,count}, daily:[{date,bet,win,profit}], byGame:[{name,profit}]}。同样确定性生成。
```

### 3.4 用户
```
GET /api/user → 先结算待开奖投注,再返回当前用户:
{id,user,name,points(真实余额),money,level, sign:{days,todaySigned,reward}, messages:[...], betlog:[最近6条投注], hongbao:[...]}。
  说明:sign/messages/hongbao 当前是示例常量,如需真实化另建表。betlog 从 bets 取最近6条,无记录时给示例。
```

### 3.5 实时回合引擎(服务端权威,核心)
```
GET /api/round?gid= → 返回该彩种当前回合状态,用于前端倒计时/期号/封盘:
{gid, game_name, interval, bet_stop_seconds, current:{period, draw_ts, seconds_left, seconds_to_stop, open}, last:{period, draw_ts, numbers, sum}}。
逻辑:
- 每彩种首次访问写 rounds_base:base_period=最新历史期+1,base_ts=对齐到 interval 的当前时刻。
- 依据 (now - base_ts)//interval 推出已完成期数 k,当前期 = base_period + k,当前期开奖时刻 = base_ts+(k+1)*interval。
- 封盘秒数 bet_stop = clamp(interval*0.25, 15, 60);seconds_to_stop = max(0, seconds_left - bet_stop);open = seconds_to_stop>0。
- 开奖号码用确定性哈希生成:sha256("{gid}:{period}") 取前3字节 %10 得三个号,sum 为和值(0~27)。保证同一期任何客户端结果一致。
```

### 3.6 投注 / 结算(真实扣豆派奖)
```
POST /api/bets  body:{gid, period, items:{"和值":金额}} →
- 校验:period 必须等于当前期且 open=true,否则 400「本期已封盘」。
- 过滤金额>0 的项,合计 total>0;校验 users.points>=total,否则 400「金豆余额不足」。
- 扣减 users.points -= total,写入 bets(status=pending, draw_ts=当前期开奖时刻)。
- 返回 {bet_id, balance(扣后余额), period, draw_ts, total}。
POST /api/bets/settle → 触发结算,返回 {settled:[...], balance}。
GET /api/user/bets?limit=30 → 先结算再返回投注记录:
  [{id,period,game,type(玩法文字),amount,result(pending/win/lose),payout,result_sum,result_numbers,time}]。
结算逻辑(settle):对所有 draw_ts<=now 的 pending 投注:
- 用确定性哈希算该期开奖 sum;派奖 payout = round(该 sum 的投注额 * ODDS[sum]);
- ODDS[s] = (1000 / 该和值组合数 ways[s]) * 0.985(即 98.5% 返还率,和值 0~27 各有不同组合数)。
- status 置 win(payout>0)/lose;payout>0 则 users.points += payout。
玩法文字规则:投注号码≤6个 → "和值 a,b,c";否则 "和值 N 个号码"。
```

### 3.7 兑换
```
POST /api/exchange body:{goods_id} →
- 校验商品存在;校验 users.points>=goods.points,否则 400「金豆不足」。
- 扣豆 users.points -= goods.points;商品 buynum+1;写 orders(status=processing)。
- 返回 {order_id, balance, name, points}。
GET /api/user/orders?limit=30 → 兑换订单列表 [{id,name,points,img,status,time}]。
```

## 5. 关键业务逻辑速查(迁移必读)

```
- 组合数 ways[s]:三位 0-9 相加得和值 s 的组合数(遍历 000~999 统计),赔率 ODDS[s]=(1000/ways[s])*0.985。
- 开奖确定性:任何一期的号码/和值 = sha256("gid:period") 前3字节各 %10;保证前后端、多客户端一致,无需存"未来"开奖。
- 回合推进:纯靠 rounds_base(base_period, base_ts)+ interval 用时间算出来,不需要定时任务;结算在 /round、/user、/user/bets、/bets/settle 被调用时惰性触发。
- 扣豆/派奖都是对 users.points 的原子自增/自减。
```

## 6. MongoDB → MySQL 迁移注意事项

```
1. group 是 MySQL 保留字 → 表字段用 grp,后端 ORM/SQL 记得别名。
2. numbers/items/columns/odds/result_numbers → MySQL JSON 类型;读写用 JSON 函数或存 JSON 字符串后应用层反序列化。
3. Mongo 的 _id(字符串,如 'u33'/'bet_...'/'ord_...')→ 直接作为 VARCHAR 主键保留。
4. *_ts(draw_ts/created_ts/settled_ts)是 Unix 秒(float)→ 用 DOUBLE 或 BIGINT;也可改 DATETIME(需同步改后端时间比较逻辑)。
5. 惰性结算改造:高并发下建议把 settle 放进事务 + 行锁(SELECT ... FOR UPDATE)避免重复派奖。
6. seeded 幂等:原用 meta.seeded_v2 标记;MySQL 可用一张 meta(k,v) 表或迁移脚本一次性导入(go28.sql 已含种子)。
7. draws 历史(~1560 期)与真实 gid/odds/interval 请从你的原始数据源(如 desheng.sql)导入,覆盖 go28.sql 中的示例/占位值。
```
